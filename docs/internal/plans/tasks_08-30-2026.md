## 1 Home State as the Global Default

> ✅ **Done 2026-08-30** — Pass 10g in `plan_design.md`. One helper
> (`apps/core/defaults.py`), every preselect surface routed through it,
> registration now requires home state, and the `_primary_state`
> fallback bug (read a nonexistent `profile.state`, always landed on PA)
> fixed on the way.

Pennsylvania is currently hardcoded as the default state throughout the app.
Replace it with the user's own `UserProfile.home_state`.

- Applies anywhere a state is preselected: listing create form, collection item
  form, wanted-list rules, browse filter initial state.
- **State only.** `home_county` stays on the profile as user information but
  prefills nothing — county is too granular to be a useful default.
- Fallback when `home_state` is null: current behavior (PA).
- No new fields. `home_state` and `home_county` already exist as FKs from Pass 6.
- Registration should require home state at minimum (see 10.26 for why).

## 3 Location Display: Stop Appending "County"

> ✅ **Done 2026-08-30** — Pass 10i in `plan_design.md`. One producer
> (`UserProfile.place` appended the unit label) fixed to "{unit},
> {state}" verbatim; the header reads *of Lycoming, Pennsylvania*; the
> collectors-card fallback matched. Audit of cards, detail pages, search
> results and letters found no other append site.

**Format:** profile header reads `of {unit}, {state}` — e.g. *of Allegheny,
Pennsylvania*.

**Fix:** remove the programmatic `County` suffix everywhere. Render the
geographic unit's stored name verbatim.

The current append produces "Baltimore County County," and there is no suffix
that works across the board: Baltimore City and Baltimore County are distinct
jurisdictions, and "Baltimore City County" is equally wrong. The unit name in the
schema is already correct and complete — nothing needs to be added to it.
Dropping the suffix entirely also reads fine for the common case (*of Allegheny,
Pennsylvania*).

Same class of bug as the ", PA" address suffix fixed in 10.7: hardcoded suffixes
bolted onto data that already carries what it needs. Audit the other append
sites — cards, listing detail, collection item detail, search results, emails.

## 4 Destructive Actions Need Two Steps

> ✅ **Done 2026-08-31** — Pass 10j in `plan_design.md`. Strike moved off
> the detail page into the edit form behind the shared photograph-confirm
> dialog (plain copy, branded trigger); no-JS falls back to a rebuilt
> plain confirm page. Draft discard on the terms page got the same second
> step. Open question resolved: modal with JS, page without. Bonus guard:
> a record can't be struck while its lot is on the market.

"Strike it from the record" currently sits next to Edit on the listing detail
page and removes the listing in one click. No confirmation, no undo.

- Remove the strike button from the listing detail page entirely. Detail page
  keeps **Edit** only.
- Move the action into the edit form.
- Clicking it opens an in-app confirmation — same styling as the existing
  image-removal confirm — requiring a second explicit click.
- **Confirmation copy is plain language, not branded.** The branding stays on the
  trigger button; the confirm states exactly what happens and that it is
  permanent, with no room to misread it. A user who doesn't know what "strike it
  from the record" means should still understand the second screen.
- Same two-step pattern for collection item deletion.

## 5 Favorites, Views & Collection Presentation

> ✅ **Favorites + listing-detail additions done 2026-08-31** — Pass 10k in
> `plan_design.md`. Corner hearts + public "N favorites" counts on every
> listing/item card and both detail pages; `view_count` (session-deduped,
> per the open question's resolution) and `published_at` (the real Listed
> date — the created_at leak was live and is fixed; relists reset both).
> **Whole-collection favoriting + the playlist presentation deferred to
> Pass 13 (owner's call)** — registered in that pass's block. Collection
> runs/rules were already marked designed-not-implemented here.

Extends 10.12, which already scopes public favorite counts. Favorites plumbing
exists and reaches the dashboard favorites page, but it isn't surfaced anywhere
else in the app.

**Favorites**

- Favorite button in the top right of every listing card and collection card. (see designs: docs\internal\design\ui-ux-redesign-model\project\uploads\ui_ux_improvement_ideas.md)
- Public favorite count at the bottom of cards and on detail pages, labeled
  "favorites" (e.g. *5 favorites*).
- Applies to listings, individual collection items, and whole collections.
- Collections become favoritable objects.

**Collection presentation (Spotify-playlist model)**

- User-written description on the collection.
- Optional user-uploaded cover image.
- Default cover when none is set: 2×2 mosaic of the first four items' featured
  images.
- Collection detail order: cover, title, description, favorite count, item grid.

**Collection rules** ("run" / "set") — designed, not implemented. A run is a
collection whose membership fills automatically: acquire an item matching the
run's criteria and it files itself there. A run describes what the user already
owns. Distinct from the wanted rules in 10.26, which describe what the user is
looking for — similar condition vocabulary, separate systems, no shared engine.

**Listing detail additions**

- **View count.** Tracking already exists; surface it. eBay-style social proof.
- **Listed date.** Must be the marketplace listing timestamp, not
  `CollectionItem.created_at`. An item added to a collection and listed months
  later shows the later date. Two distinct timestamps — verify no code path leaks
  the collection date onto a marketplace listing. Items listed directly (never a
  collection item first) are unaffected.

## 6 Wanted List as Rules

Extends and largely supersedes the wanted-list alert bullet in 10.14. Reconcile
terminology before building — the dev plan calls this "Looking For."

A wanted rule describes an item the user does **not** own and wants to find. Not
to be confused with the collection run rules in 10.25, which auto-file items the
user already owns.

**Bug first:** the Wanted List tab in the dashboard redirects to My Collection.
Likely a URL or view routing error.

**Model**

- Maximum 10 wanted rules per user.
- A rule is a set of criteria over the existing item taxonomy: state, geographic
  unit, year or era, item kind (license / stamp / tag / add-on), class,
  species/method facets. Any subset is valid — a rule can be as broad as *any
  Pennsylvania item* or as narrow as a single county and year.
- Multi-dimensional, with AND/OR between conditions. Cap conditions per rule
  (number TBD) so it can't get ridiculous.
- Rules do **not** auto-delete when the user acquires a matching item. A rule is a
  standing interest, not a single want.

**UI constraint (hard).** The user base skews older and non-technical. The
builder must read as plain language — assembled sentences, not a boolean query
builder. This is the main design risk in this item and should be prototyped
before the backend is finalized.

**Wanted List page**

- Two columns: Priority, Rule.
- Subtle per-row edit control.
- Up/down carets on each row to reorder priority.
- Add and delete per rule.
- Priority feeds recommendation ranking.

**Seeded rule.** On account creation, generate one rule: *any item from
{home_state}*. Fully deletable like any other. It exists so no user starts with
zero signal for the recommendation algorithm.
