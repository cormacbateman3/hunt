Your "lowest level builds up" instinct only truly applies to geography (State → Unit). The license-type dimensions are deliberately flat, state-scoped value lists — the state FK is scoping, not a hierarchy level. So yes, your read is right: state is the only hard dynamic today; item_kind adds the second structural axis, and year ranges add a soft third.

2. Dependencies are soft on purpose — and your non-resident example is the proof. The intuitive rule "non-resident → no county, statewide" is actually wrong for PA: nonresident artifacts print "OUT-OF-STATE Co. 68" — they carry a unit. That's why the model treats dimensions as independent descriptors of what's printed on the artifact rather than a constrained catalog of legal products: sellers tag what they can read off a 60-year-old item, and hard combinatorial rules would block legitimate oddities. The doc now has a table of every cross-dimension dependency and whether it's hard (state scoping, unit-belongs-to-state, year floor) or soft (year↔addon plausibility, nonresident hints, prefill inferences). One more thing worth knowing: the product grain you're missing does exist — each raw license_classes.csv row is a product (Resident × Hunting × Annual = "PA Resident Hunting License"). The cleaning script explodes those combos and throws the product row away — same harm as the facet flattening. We shouldn't build a LicenseProduct table now, but that file stays authoritative so a future product dimension costs nothing to derive.

3. Lot — you're right, and that's already the plan. "Lot is a feature of the listing, not the license" is exactly decision 1 in the doc (now marked confirmed): 10.15's inventory_format on Listing owns it, with contents in ListingLotItem. Your dependency instinct is also the reason: when lot is selected, the single-artifact fields collapse because the listing isn't describing one artifact anymore — the per-item dimensions belong to the lot's contents, not the listing. That collapse logic lives in the listing form (10.15), never in the item taxonomy.

4. states.csv years — correct reading. min_license_year is the state-level artifact floor ("earliest known license year for this state," already enforced in form validation), and licensing_start_year is when licensing legally began (context only). Neither says anything about a specific product — that's precisely the level T4 adds: LicenseType.first_year/last_year. So time becomes a clean two-level hierarchy matching your instinct: state floor → product span → the item's actual year.

On maintenance/governance — agreed it's a dev workaround, and the doc now has a two-phase plan (plus T11). Phase A ships with this work: ref_data/ is the only hand-edited layer; seeders stop clobbering (create-missing-only + drift report by default, --overwrite for dev resets — without this, the admin year/facet edits you've started making get silently erased on the next seed); a ReferenceDataSuggestion admin action "Approve → create/update LicenseType" (the missing back half of your Filter Cleanliness Rule); and a "Merge into…" admin action for dupes. Colors/shapes stay code constants in constants.py as the single source (10.8 already extends them in code) — the duplicate lists come out of the cleaning script. Phase B at 10.18 inverts the flow: a manage.py export_reference_data command writes DB → CSV so admin edits get versioned in git, and from beta onward the DB is the system of record with CSVs as bootstrap/backup only.
